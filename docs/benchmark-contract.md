# Benchmark contract (v1)

This defines what a published result must mean for issue #7. The JSON formats are in
[`validation-v1.schema.json`](../benchmarks/schema/validation-v1.schema.json)
and [`benchmark-v1.schema.json`](../benchmarks/schema/benchmark-v1.schema.json).
The contract applies to CPU, CUDA, Vulkan, and Core ML. A benchmark report is
evidence about a particular build, checkpoint, precision, host, and workload;
it is not a model-quality score.

## Two separate corpora

**Acceptance** uses the committed `benchmarks/cases/acceptance-250.json` file,
identified by SHA-256
`cd991ea8d6c4ac2124f96672d0552780e2ae06839313f147f1f1ac9af6d3bab4`.
It contains 250 one-question requests: 100 choice, 75 score, and 75 noul, in
25 scenarios. Every request is evaluated at batch sizes 1, 2, 4, and 8 for
each checkpoint and precision being claimed. Acceptance requires exact
categorical values and structure, plus absolute error at most 0.0001 for each
public numeric field. Tokenization and raw tensor checks remain separate
diagnostics. A failing acceptance run makes any associated speedup ineligible
for publication.

**Performance** has its own versioned, committed corpus and SHA-256. The
[`performance-v1`](../benchmarks/cases/performance-v1/manifest.json)
corpus contains **10,240 questions in 4,800 requests**, generated by
[`make_performance_corpus.py`](../benchmarks/make_performance_corpus.py). It has
16 strata: four state-length bands crossed with one, two, four, or eight
questions per request. Every stratum contains 640 questions and has its own
file and SHA-256 in the manifest. Choice, score, and noul tasks rotate through
each stratum; multi-question requests contain output-type combinations. This
is a separate workload from the acceptance corpus.

Its 512 source contexts were generated once with the local text model and
committed in [`source-notes.json`](../benchmarks/cases/performance-v1/source-notes.json)
with the model identifier, prompts, sampling settings, and seeds. The corpus
generator reads those committed texts; benchmark runs never call a text model.

| Length band | Approximate state length | Purpose |
| --- | --- | --- |
| `short` | 160 characters | Interactive latency |
| `medium` | 480 characters | Typical context |
| `long` | 1,500 characters | Longer context |
| `limit` | 3,300 characters | Truncation and token-budget cost |

The length bands are defined by source characters, not exact model tokens; each
checkpoint may tokenize them differently. Results identify each stratum and
must not collapse them into one average. The corpus uses synthetic records,
stable request IDs, fixed ordering, and no personal data. The deterministic
generator and tests must reproduce the committed files.
The acceptance gate is run first on its own corpus; the performance corpus is
then checked for answer parity before its timings are accepted. Corpus changes
create a new version and cannot be merged into older trend lines. The workload
manifest and its SHA-256 must be published with each report. The corpus and
strata are fixed for version 1.

## Benchmark matrix

One report covers one host, checkpoint, precision, candidate build, baseline
build, performance corpus, and timing track. Keep these dimensions separate:

| Dimension | Required settings |
| --- | --- |
| Checkpoint | `english`, `multilingual`, `typed-decisions` as separate reports |
| Precision | Match native and Python arithmetic; label FP32, BF16, or FP16 |
| Inference batch | 1, 2, 4, 8 requests per forward call; final partial group retained |
| CPU threads | 1 and a stated host-specific physical-core setting; same thread budget for both systems |
| HTTP concurrency | 1, 2, 4, 8 clients in a separate track; report observed batch sizes |

GPU reports record the exact device and driver. CPU reports must work on a host
without a GPU. A CPU comparison uses a CPU-only native build and a CPU Python
baseline at matching precision, with explicit native, PyTorch, and BLAS thread
settings. Record affinity and frequency policy if set. Do not infer a speedup
from two runs made on different hosts or under different thread budgets.

The **inference track** times preparation, model execution, calibration, and
answer construction. It excludes process startup, model load, JSON transport,
and queue waiting. Batch latency is measured per call, and throughput is the
number of questions divided by the sum of timed call durations. Warm each
request group three times; use at least five timed passes through the entire
stratum, alternating baseline/candidate order. Keep the complete sample arrays.
Report p50/p95 batch latency and questions/second for each stratum and batch size.

The **HTTP track** measures client-observed request latency and sustained
questions/second at each concurrency. It includes serialization, transport,
and server queue time. It records the server batching settings and observed
batch-size distribution. Keep HTTP results separate from inference results;
their latency units differ. Warmup and measurement duration must be recorded.

Measure model load time from process start to ready-to-answer, separately for
each system. Measure peak resident memory of each process independently, not
the combined peak of both systems. State whether the OS page cache was warm;
do not describe a page-cache-warm load as cold. Report both startup and memory
even when they are outside the timed inference loop.

## JSON report

The **validation JSON** stores the complete matching-precision baseline
(`expected`) and native (`actual`) public answer for every acceptance request
at every batch size. It also stores the request ID, precision, checkpoint and
corpus hashes, per-case numeric error, and each categorical, numeric, or
structural mismatch. The historical validation summaries contain only aggregate
errors and failure IDs; they are not substitutes for these per-case comparison
values. A published report must include or link its validation JSON, so readers
can inspect exactly what was compared. The expected answer is tied to the
baseline revision and device; it is not an assertion that all hardware produces
bit-identical floating-point values.

The **benchmark JSON** requires a run status, identities for the separate
performance corpus, weights, builds, acceptance report, and performance-workload
parity report, hardware and software details, exact build and command-line
flags, thread settings, explicit timing boundaries, and raw latency samples.
Every result row identifies its stratum and batch size or HTTP concurrency. A
failed or incomplete row has `speedup: null`; do not fill it with a measured
ratio. Keep full machine-readable reports as artifacts; human-readable tables
are derived views, never the sole evidence.

Report timestamps use UTC. All durations are milliseconds; memory is bytes.
`questions_per_second` counts questions, not requests. The `samples_ms` array
contains one observation per timed batch call in inference mode, or one per
completed client request in HTTP mode. Summaries must be recomputable from
those samples and the recorded question count and total measured wall time.
Missing startup or memory measurements use `null` with a reason. A missing
timed row makes the report `incomplete`; it must not contain fabricated zero
samples.

The schema is independent of a particular backend. A contributor
can run the same corpus and produce the same JSON shape on a CPU-only machine.
The existing GPU reports remain historical evidence in their original format;
this contract does not retroactively re-label or convert them.
